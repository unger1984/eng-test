## Аутентификация

Для аутентификации в этом репозитории используется jwt токен. Технология известная, зарекомендовавшая себя.
Давайте в ней усомнимся. Как минимум - в целесообразности гонять в каждом http запросе такой большой кусок данных.
Расскажите о проектах с вашим участием, где использовалась другая техника авторизации.
Если в таких проектах вы бы могли выбирать - выбрали бы вы аутентификацию через jwt? Если да, то почему?
В каком проекте, в котором вы участвовали, вы бы наоборот, вместо jwt выбрали что-то другое и почему?

**Ответ.** В админке для операторов делали сессии — session ID в куке, состояние в Redis. JWT там специально не использовали: один домен, мобилок нет, зато нужно было уметь моментально рвать сессию при смене ролей или блокировке. Я бы и сейчас там выбрал сессии — меньше мусора в запросах, понятный logout, проще смотреть кто онлайн.

В B2B-платформе с мобилкой и несколькими фронтами был JWT. Там он уместен — клиенты независимые, бэкенд stateless, масштабируется без обмена сессиями. OAuth с refresh-токенами рассматривали, но для наших объёмов JWT хватило.

Где бы JWT не использовал — публичный API с очень частыми запросами. Там каждый запрос тащит большой токен, парсинг на каждый вызов. Лучше короткий session token в куке или заголовке, проверка в Redis — меньше CPU и трафика.

## Идентификация

В этом репозтории в некоторых таблицах для идентификации записи используется uuid. Эта техника удобна по нескольким параметрам.
Сложно представить, чтобы использование uuid во всех таблицах - как стандарта - создало бы где нибудь проблему.
Но может быть в вашей практике встречались случаи, где uuid как идентификатор стал проблемой или мог бы стать проблемой?
Опишите где и почему.

**Ответ.** UUID юзал много где, проблем не было. Пока не попался проект с интеграцией во внешнюю систему — у них только короткие числовые ID, по длине ограничения. Пришлось держать два ключа, маппинг, синхронизация. Можно было изначально завести числовой ID для интеграционных сущностей.

В практике с остальным не сталкивался, но знаю о таких кейсах. Например лог-агрегация с пачками событий — UUID на клиенте, десятки тысяч в минуту, индексы могут распухать быстрее чем с ULID или snowflake-like ID. ULID остаётся unique, но упорядочен по времени и короче — для логов это плюс.

Или join'ы в аналитике — UUID 16 байт против 4–8 у bigint. При миллионах записей и частых джойнах разница в размере индексов и времени выполнения может быть заметна. Для обычного OLTP обычно не критично, а в data pipeline'ах с большими объёмами я бы задумался о компактных ID.

## Организация кода

В этом репозитории, серверный код сделан на базе NestJS.
DI, services, controllers, middleware, decorators - в этом, как и во многих других подходах есть плюсы и выгоды.
Расскажите с примерами из опыта о реальной пользе того или иного механизма организации кода лично для вас или
для вашей команды, а может быть - для компании. Если есть какой-то механим, который также - для вас, команды
или компании наоборот - создавал сложности - тоже расскажите.

**Ответ.** DI в NestJS — в первую очередь для тестов. Подменяешь нужный модуль, не ищешь все зависимости руками. В проекте с расчётами и внешними API тестили сервисы через `overrideProvider`, моками репо и HTTP. Без DI пришлось бы фабрики городить или синглтоны глобальные.

Декораторы — `@Body()`, `class-validator`, `@UseGuards()` — заметно урезали boilerplate. Меньше ручных проверок, единый стиль в команде.

Минусы — перебор с модулями. Один сервис оброс кучей `imports`, зависимости по разным файлам разъехались, циклы через `forwardRef` решали. Это не NestJS виноват, а мы перестарались с гранулярностью. Пришлось модули по доменам объединять. DI и модульность — хорошо, но баланс нужен.

## Реактивность

В этом репозитории, для интерфейса используется React. Его название связано с реактивным подходом к отрисовке
интерфейса - мы меняем состояние, а интерфейс перерисовывается в соответствии с этим.
Сам посыл подкупает - разработчик заботится о состоянии, остальное за него делает фреймворк.
Такой подход, конечно, помимо React реализуют и многие другие фреймворки.
Были ли ситуации в вашем опыте, когда реактивность была не плюсом, а помехой? Если да, расскажите на примере.
Если был опыт построения рендера интерфеса на другом принципе, раскажите на каком и какие были резльтаты?
Расскажите на конкретных примерах, что вам доставляет неудобства в том, как реактивность реализована
непосредственно во фреймворке React?

**Ответ.** Мешала на тяжёлой форме — десятки полей, сложная валидация. Каждое изменение state тянет полный ререндер со всеми вычислениями. Лаги при вводе. Выкручивались выносом тяжёлых полей в отдельные компоненты, `React.memo`, дробили state. Не реактивность виновата, а то что всё перерисовывается без оптимизации.

Что не нравится в React: `useEffect` с dependency array — легко наловить race conditions, лишние запросы, отладка головная боль. Приходится тащить React Query или SWR. Я сам стараюсь в компонентах useEffect не держать — только в кастомных хуках и по минимуму.

Батчинг state — в хендлерах батчится, в setTimeout/Promise нет. Неочевидно когда и как. И key в списках — неверный key ломает фокус и локальное состояние. Классическая ловушка для новичков, в доках не везде про это пишут.

## Инфраструктура

Добавил ESLint, Prettier, Husky и pre-commit хуки — ловит косяки до коммита (unused vars, any и т.д.), выравнивает стиль, не даёт закоммитить битый код. lint-staged гоняет проверки только по изменённым файлам, в review меньше мусора, в main меньше сломанного.

В корне: package.json с зависимостями, .prettierrc, eslint.config.js на весь проект, .husky/pre-commit вызывает lint-staged. Команды: `npm run lint`, `npm run lint:fix`, `npm run format`, `npm run format:check`, `npm run test`.

**Тесты** — Jest в server, unit-тесты для GamesService (scoreFromTapsCount, isRoundActive, getRoundStatus, processTap) и AuthService (validateUser, login, роли admin/nikita/user). `npm run test` в server или из корня.
